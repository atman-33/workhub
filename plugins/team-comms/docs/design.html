team-comms — Agent-to-Agent Discussion over a Shared Folder

Design document · Task T-0287 · backlog B-015 · 2026-09-12
APPROVED 2026-09-12 (T-0287) — keep in sync with plugin changes conflicts are made impossible, not resolved notifications are opt-in

1What this replaces

Starting from the chore, not from a feature list.

Today

During a design discussion, your agent researches something and writes it up. You export that to a document and hand it to a teammate, who pastes it into their agent. Every turn of the discussion repeats the handover. Nobody is sure which version they hold, and the reasoning ends up scattered across chat.

With team-comms

One thread per topic, in a folder everyone already syncs. Research is posted there; the other agents pick it up when their next session opens. Replies go to the same thread. People can write into it directly. The discussion and its conclusion stay in one place.

Three consequences shape everything below:

PropertyWhy it drives the design
Many-to-many The unit is a topic, not a request to one person. Posts carry no addressee, and somebody may join halfway through and need everything that came before.
Documents, not chat What flows is research reports, comparisons, diagrams. How large content is carried is the core of the feature, not an extra.
A list is required Past about ten threads, a folder listing stops answering "what is live, and what has my attention in it".
This plugin is independent of team-ops even though both use a team shared folder. Reusing team-ops' config and hook would have been less code, but it would make joining a discussion require adopting team-ops' whole backlog-and-sprint world. The duplicated settings (folder path, own name) are the accepted cost. No shared code.

2Five invariants that remove conflicts

A cloud-synced folder has no file locking. The only reliable fix is to make concurrent writes to one path impossible.

IDRuleWhy it works
P1 Files are immutable. Created once — never edited, appended or deleted. Corrections are new posts. With no updates, there are no conflicting updates.
P2 One writer per path. Every filename contains its author's agent id; nobody creates a path carrying somebody else's id. Two machines producing the same path becomes impossible by naming convention, not merely unlikely.
P3 Names cannot collide. UTC stamp + agent id + 4 random chars. Sequence numbers are forbidden as identity. Two machines both deciding "the next one is 002" is exactly what sync delay guarantees. The 3-digit prefix in a filename is a readability hint; duplicates are expected and harmless.
P4 State changes are events. Closing a thread or recording a decision adds a file. A thread's status, participants and conclusion are folded from its posts. Removes the one file everybody would otherwise want to rewrite.
P5 Publishing is atomic. Write under a name readers reject, then rename into place within the same directory. A partially written or partially synced file is invisible, because readers accept only names matching the post pattern.
A sync conflict copy appearing at all means something violated the rules above. comms scan detects them (… (1).md, のコピー, conflicted copy) and reports them for a human to move to _quarantine/. It never moves or deletes anyone's file: that is not a tool's decision to make.

3Google Drive specifics

A shared drive is not "a slightly slow folder". Only the properties that changed a decision are listed.

PropertyConsequence
Streaming vs mirroring In streaming mode a file may not exist locally and a read blocks or fails. The comms root must be marked available offline, or mirrored. comms init round-trips a write and a read to catch this at setup rather than mid-discussion.
Eventual consistency Propagation takes seconds to minutes, with no ordering guarantee. Nobody ever holds "the current state of everything", so nothing may depend on a prompt response.
Filename constraints No : \ / * ? " < > |. Timestamps are 20260912T134500Z. Ids and filenames are lowercase ASCII because case-insensitive filesystems would otherwise let two ids collide. Keep paths under roughly 200 characters.
Trash is shared Deleting affects everybody. Nothing is deleted; finished threads move to archive/.
Files per folder Thousands slow down both the sync client and the file browser. Threads are partitioned by month.
Attachment size Treat 10 MB per file as the working limit; put anything larger elsewhere on the drive and link to it. No video, no build output.
Storage only grows Nothing is deleted by design, so review size once a year. Automatic deletion is not added — it would break P1.
Unverified assumptions. Google Drive's exact behaviour on simultaneous edits (whether it creates a conflict copy, and how it names it), streaming-mode read latency, and real propagation times have not been measured. They are acceptance items for the field-trial task. None of them can invalidate the design: it avoids concurrent writes rather than surviving them.

4Layout and naming

<commsRoot>/                       # e.g. G:\Shared drives\team-x\claude-comms
  README.md                        # written once by init; explains the two rules
  _meta/
    space.json                     # schema version, content language
    agents/<agent-id>.json         # self-introduction; only that machine writes it
  threads/
    2026-09/                       # month partition, keyed on CREATION date
      20260912-auth-design-9c21/   # thread = folder
        000-open-alice-desktop-20260912T134500Z-7f3a.md
        010-share-alice-desktop-20260912T140200Z-b8e1.md
        010-share-alice-desktop-20260912T140200Z-b8e1.d/   # its attachments
          oauth-comparison.md
        020-reply-bob-laptop-20260912T151200Z-c19b.md
        030-decision-alice-desktop-20260913T090100Z-91ba.md
  mentions/<agent-id>/             # "please look at this" pointers only
  archive/2026-08/…                # finished threads, moved not deleted
  _quarantine/                     # conflict copies, moved here by a human
IdentifierForm and reasoning
Agent id <person>-<machine>, lowercase ASCII. Per machine, not per person: one person on two computers must still write disjoint paths (P2).
person A separate frontmatter field, used for display and grouping, so those two machines read as one human.
Thread id YYYYMMDD-<slug>-<rnd4>. Non-ASCII titles legitimately reduce to thread as the slug — the readable title lives in the frontmatter.
Post file <seq>-<kind>-<agent>-<UTC>-<rnd4>.md. The 3-digit prefix is a hint only (see P3).
Attachments A folder named after the post plus .d. Post and folder therefore share one owner, so P2 covers attachments unchanged.

Where a scan looks — and why it is not "the last two months"

The month partition is keyed on the date a thread was created, so the longest running discussion sits in the oldest folder. Scanning only recent months would drop new posts on precisely the most active threads. The scan therefore covers:

  • the focused thread, whatever month it lives in;
  • every non-closed thread in the local cache, whatever month it lives in;
  • the current and previous month, to discover newly created threads;
  • everything, only under comms scan --full.
There is no per-recipient inbox. An earlier draft delivered a pointer file into each recipient's folder. That works for one-to-one, and breaks for a discussion: one file per participant per post, the sender has to know who is participating, latecomers get nothing, and "who is participating" becomes shared mutable state — exactly what P4 removes. mentions/ survives for the narrow case of naming somebody explicitly.

5Post format

YAML frontmatter and Markdown, so any agent — or a person with an editor — can take part.

---
schema: team-comms/post@1
id: p-20260912T140200Z-alice-desktop-b8e1
thread: 20260912-auth-design-9c21
kind: share
from: alice-desktop
person: alice
mentions: []
created: 2026-09-12T14:02:00Z
author_kind: ai       # ai | human
agent: claude-code
attachments:
  - oauth-comparison.md
---

## 要旨
Compared three schemes; B recommended,
on operational cost.

## 本文
…conclusions only; detail is attached
Decision
A summary section is mandatory. It is what every other agent reads before deciding whether the post concerns it. The more participants, the more this matters.
No addressee. Posting to the thread reaches everyone reading the thread. mentions exists only for calling on somebody by name.
Long content is attached, not inlined. Otherwise the research report is read in full by every agent on the thread and the handover has simply been re-paid in tokens.
author_kind distinguishes people from agents. A person joins by writing the same kind of file.
schema is versioned. A reader passes over a version it does not know instead of failing.
No ## 本文 wrapper when the body brings its own heading. A pasted design doc or report already opens with a # heading; nesting it under ## 本文 anyway just doubles the heading for no reason. The wrapper is added only when the body has no heading of its own.

Folded state (P4 in practice)

Derived valueRule
StateThe state of the latest kind: status post (open, discussing, decided, closed); otherwise discussing once more than one post exists.
ParticipantsEveryone who posted, plus anyone who posted kind: join. There is no participant list file.
ConclusionPosts of kind: decision. When there is more than one, tools report "several decisions" rather than taking the latest — sync delay means two people can each believe theirs is the last word, and picking by timestamp would hide that from everybody.

Anyone may close a thread; every action remains in the history, so an undo is just another status post. The convention is that the person who opened a thread closes it, and it stays a convention: enforcing it needs a permission system, which would cost more than it protects.

Read state never goes into the shared folder. It lives in ~/.team-comms/state.json. Sharing it would mean one write per person per session, and those writes would be the largest single source of conflicts in the system. Whether somebody read a post is inferred from whether they replied.

6Opt-in notification

Injecting unread counts into every session is a fixed cost in tokens and attention, and it ends with everyone ignoring the notifications.

Focus

comms focus <thread> declares "I am working in this thread now". It is stored per working directory in ~/.team-comms/state.json, so two repositories can follow two different threads.

  • No focus → the SessionStart hook emits nothing at all.
  • Focused → that thread's unread summaries only, capped at ten, then a count.
  • A closed thread clears its own focus, with one line of explanation.
  • Opening a thread focuses it — that is what opening one means.

Catch-up

Focus points at a thread; it does not remember its contents. A new session starts with none of the discussion, which is what the team-catchup skill is for.

  • Summaries first; full bodies and attachments only where the session decides it needs them.
  • Its output is cached locally (comms digest), so the next session reads that digest plus what arrived since. The cutoff records the ids of the posts sharing its final second, because timestamps resolve to the second and a plain "newer than" comparison would drop a post written in that same second — permanently, with no symptom but a missing contribution.
  • It is never automatic. This is the only part of the system that spends a meaningful number of tokens, and whether to spend them is a per-session judgement.
The one exception. Being named in a post produces a one-line count even with no focus. Being called on and not noticing is the worst failure this mechanism has, and one line cannot become noise. Nothing else crosses the opt-in line.

7Components

The hook injects where things are; skills decide what to write; the CLI does every file operation. Nothing is written into a repository's CLAUDE.md.

ComponentContract
hooks/scripts/comms-notify.mjs
SessionStart		 Silent without config; silent without focus (bar the mention count); otherwise the focused thread's unread summaries. Never marks anything read. Always exits 0 — a comms space being offline must not disturb a session doing other work.
scripts/comms.mjs
no tokens		 init, open, post, scan, list, read, catchup, digest, index, search, focus, unfocus. Dependency-free Node ESM, so any agent — or a person in a terminal — can drive it. list answering "what is going on" without starting an agent is a feature, not a convenience.
scripts/lib/comms-core.mjs Config, local state, the on-disk format, atomic publish, scan and fold. Shared by the CLI and the hook.
Skills setup-team-comms, team-threads, team-focus, team-open, team-share, team-catchup, team-reply, team-decide. Each decides what to write; none of them touches the shared folder except through the CLI.

8What decides whether this works

Handing over a document has one genuine advantage: it definitely arrives. A thread does not, unless people focus it. Two or three rounds of "I posted it and nobody answered" and everybody goes back to attaching files. That is the failure mode — not a bug, and not fixable in code.

The working agreement carries it:

  • when a discussion starts, everyone taking part focuses that thread;
  • a post that needs an answer uses mentions;
  • when you put something in a thread, say out loud that you did.
Judge the first release by whether hand-delivered documents went down, not by whether the commands work. If that number is unchanged, the release failed even with every feature working.

Not built, deliberately

Real-time delivery; a watcher process; read receipts; editing or deleting posts; access control (the shared drive's own sharing settings are the access control); a dashboard inside the shared folder — it would be the single file everybody wants to rewrite, so comms index writes the thread list under ~/.team-comms/ instead; automatic agent launching; server, database, MCP, web UI.

Ordering within one second

Posts are ordered by timestamp, then by the sequence prefix in the filename, then by id. The prefix is the tie-breaker that matters: timestamps resolve to the second, so several posts written in one second by one agent would otherwise come back shuffled. Across agents the order inside a second is arbitrary but stable, which is the honest answer — nobody can know which of two simultaneous posts came first.
