# 書き直しの手順

既存の文章を直すときの手順。新規に書く場合は SKILL.md の §1〜§2 と `writing-constitution.md` に従う。先に `meaning-preservation.md` を読む。

## 1. 文脈と段落を把握する

書き直す前に、文章全体の流れを確かめる。

1. **ジャンルを判定する**: 技術記事、業務・仕様書、エッセイのどれに近いか。ジャンルごとの注意は §5。
2. **段落ごとに話題を1行でつかむ**: 話題の違う段落同士はまとめない。1つの段落に話題が混ざっていれば、文の順序を保ったまま分けることを検討する。
3. **文ごとに、前の文との関係を確かめる**: 理由、例示、但し書き、言い換え、補足、まとめのどれか。このメモは出力に出さない。
4. **意味の4点を確かめる**: 主張、比重、言い切りの強さ、文の働き。

## 2. 変換する

次の順に直す。どれも、元の文から分かる範囲で行い、`meaning-preservation.md` の4点を動かさない。

1. **誰が・何を・どうしたかを明確にする**: 動作主や対象は、前後の文にあるときだけ補う。受動態や指示語（「これ」「両者」「片方」）の多用は、指す先が分かるときだけ名詞に戻す。
2. **文末の働きは元のまま保つ**: 説明文の言い切りを、勝手に「〜できます」や「〜してください」に変えない。
3. **比喩動詞を平易な言葉に開く**: 「倒す」「効く」「溶かす」「潰す」など。含みは残す。語は `forbidden-patterns.md` を見る。
4. **擬人化を解体する**: 感情や意志を持たせている表現に限る。
5. **補足カッコと、英単語前後の余計な半角空白を削る**: 情報量が増えない言い換えカッコだけ。
6. **「重要なのは」と否定対比を整える**: 評価や主張を担っているなら残す。
7. **絵文字、文末コロン、ダッシュ記号を外す**: ダッシュは助詞や句読点に置き換える。
8. **接続を確かめる**: 「ただし」「しかし」「また」「そのため」などのつなぎ言葉、主題の「も」、文頭の指示語は、前後の文と何をつないでいるかを確かめる。接続の根拠が前後から分かれば適切な接続に直し、分からなければ直さず「書き手に確かめたい点」に出す。「自然に読めるか」という感覚だけで決めない。
9. **予告だけの文を解消する**: 「次の点があります」「注目すべき点があります」のように中身のない予告は、予告が担っていた重み（「注目すべき」など）を述語に残しながら、続く中身の文と1文にまとめる。まとめると意味が変わるなら残す。
10. **主語と述語がかみ合わない文を整える**: 元の意図が読み取れる範囲で。
11. **文の長さと読点を整える**: 平均30〜45字、1文の読点は0〜2個が目安（実務上の目安であり、規則ではない）。60字を超える長い複文は2文に分けることを検討する。10字未満の短文を連打して劇画調にしない。漢語が連なって硬いところは、平仮名や動詞に開く。
12. **文末のリズム**: 同じ文末が3文以上続くときだけ、直すついでに散らす。

## 3. 機械チェック

書き直したら、`scripts/lint.mjs` と `scripts/diff.mjs` を使う。どちらも node だけで動く。

```bash
node <スキルのディレクトリ>/scripts/lint.mjs <書き直したファイル>
node <スキルのディレクトリ>/scripts/diff.mjs <元のファイル> <書き直したファイル>
```

- **lint**: 絵文字、文末コロン、ダッシュ、和欧文間の空白、太字・箇条書きの多用、同じ文末の連続、比喩動詞・前置き・頻出語を指す。指摘は見直し候補で、命令ではない。評価を担う語（「大事です」）や、主張に必要な否定は、指摘されても残す。修正は2周までにし、警告を消すためだけの言い換えを繰り返さない。
- **diff**: 元の文と書き直した文を比べ、意味が動きやすい箇所を挙げる。出力される候補を1つずつ確認する。
  - 依頼・義務・評価・可能・推量などの言い回しの種類が増減していれば、元の働きからずれていないか見る。ずれていれば元に戻し、正当な言い換えなら「変えたところ」に載せる。
  - 元にない語は、勝手な付け足しがないか。消えた語は、必要な前提の脱落がないか。
  - 箇条書きを地の文にしたとき、評価や義務が足されていないか。段落をまとめたとき、話題が混ざっていないか。
  - つながりを確かめる箇所は、前後の文とつながっているか。
  - 修正は1回だけにし、再実行を繰り返さない。

node が使えない環境では、同じ観点（言い回しの増減、元にない語、消えた語、段落・箇条書きの変化、接続）を目視で確かめる。

## 4. 出力の形

対話で書き直した結果を返すときは、次の形にする。絵文字や余計なカッコは使わない。

```markdown
### 書き直した本文

（書き直した本文）

### 変えたところ
- 元の表現 → 書き直し後の表現（理由を短く）
（意味が動きやすい変更、つながりを直したところ、補ったものだけを、最大5点まで。該当がなければ「なし」と1行で書く）

### 残したAIっぽいところ
- （残した表現と、削るかどうか書き手へ確認する問い）
（意味や重みを担っているため消さずに残した前置きや結びがあるときだけ。なければこの見出しごと出さない）

### 書き手に確かめたい点
- （確認したい前提や条件を1〜2点）
（判断に迷った点や、前後のつながりが特定できなかった点があるときだけ、最大2点。なければこの見出しごと出さない）
```

ファイルを直接編集する依頼のときは、本文を差し替えたうえで、この3つの見出しは返答に書く。

## 5. ジャンル別の注意

### 技術記事

- 太字は1,000字あたり1〜2箇所まで。論理の展開を箇条書きに頼らず、地の文で書く。箇条書きは全体の15%以下が目安。
- 箇条書きを地の文に統合するときは、各項目の文末の働きを保つ。並列の項目なら箇条書きのまま残してよい。
- 絵文字、文末コロン、ダッシュは使わない。短い記事には「まとめ」見出しを置かない。
- 元の文や前後の資料にある情報の範囲で、手順や設定を整理する。元にないコマンドやコード片を作って足さない。
- 冒頭の空疎な前置き（「近年、AI技術の発展は目覚ましく…」）は削り、課題や前提条件から書き始める。「本稿では」「筆者は」のような論文調も避ける。
- 漢字の比率は20%前後を目安に、漢語が連なるところは和語や動詞に開く。

### 業務・仕様書（PR説明文、社内レポート、提案書）

- 比喩は、誤読の原因になるので客観的な言い方に改める。ただし含みや理由は削らない。
- 受動態で曖昧な箇所は、元の文や前後の資料から主体が特定できるときだけ「開発チームで合意した」のように主体を書く。特定できなければ架空の人物や役職を作らず、事実として書く。
- 「適宜対応する」のような曖昧な表現は、元の資料に具体的な条件（エラーコード、再試行回数など）があるときだけ具体化する。資料にない条件や数値を作らない。
- 「検討にあたっては多角的な視点を考慮し…」のような前置きは削り、結論や要請事項から書き始める。
- 「これらを理解すれば業務効率が飛躍的に向上します」のような、読んだ効果の押し付けは削る。

### エッセイ・個人発信（note、ブログ）

- 日常の小さな発見や感想を、教訓にしない。「美味しかった」「疲れた」のような素直な実感を残す。壮大化の熟語（`forbidden-patterns.md` を参照）は平易な言葉に戻す。
- 書き手の視点と、「〜かもしれない」のような主観の揺らぎは、元のニュアンスに応じて残す。客観的な説明文を、個人の日記のような文体に作り替えない。
- 元の文にない五感の描写（冷房の温度、周囲の音など）を足さない。
- 「〜してみてはいかがでしょうか」「ぜひ参考にしてみてください」のような定型の結びを削る。最後の段落で、社会や未来への提言を無理に置かない。
- 絵文字と文末コロンは使わない。
